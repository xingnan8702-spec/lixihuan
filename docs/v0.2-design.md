# v0.2 iPad 数据面设计

## 1. 文档状态与实现边界

本文定义 v0.2 的可执行设计和失败契约，不表示这些能力已经交付。

当前基线如下：

- Go relay 与本地 SOCKS5 client 已实现 TLS 1.3、token 认证、TCP CONNECT 和 UDP ASSOCIATE。
- Swift `IPadProxyCore` 已实现协议编解码、令牌脱敏、规则引擎、`FlowRouter`、基础 `DNSProxyCore`、有界 `FakeIPStore`、基础 `RuleStore` 和 transport/credential 协议，可在 Linux 运行单元测试。
- Apple-only template 已包含 `NetworkFrameworkTLSTransport`、`NetworkFrameworkDirectTransport`、`KeychainCredentialStore`、`AppGroupConfigurationStore` 和基础 `PacketTunnelProvider` 生命周期代码，但它们不属于 SwiftPM/Linux target，尚未经过 Xcode、iOS SDK 或真机验证。
- 当前 DNS core 对 `PROXY` A/AAAA 合成 FakeIP；对 `DIRECT` 和其他需转发的 qtype 返回携带明确 `RoutingAction` 的 forward 决策，并支持一个 EDNS(0) OPT。上游 I/O、negative response、CNAME 和 TC retry 仍属于 Packet Tunnel 接入工作。
- 当前 FakeIP core 使用固定权威 TTL、flow lease、correlation grace 和 reuse quarantine；访问不会续期，有 lease 的映射不会回收，地址隔离期结束前不会复用。当前 RuleStore 提供 32 MiB 输入上限、decode/compile 后的 Foundation `.atomic` 写入和内存快照交换。manifest/current/previous 恢复仍未实现。
- `PacketTunnelProvider.makeDependencies()` 仍会抛出 `missingDependencies`。仓库当前没有可运行的 user-space TCP/IP stack 适配器、Xcode containing app/extension 工程、entitlement、provisioning 或可安装产物。
- v1 transport 是 TLS over TCP。QUIC 不属于 v0.2，也不得从本文推断为已实现。

完成状态只能以 [v0.2 验收文档](v0.2-acceptance.md)中的证据为准。

## 2. v0.2 范围

v0.2 要把 iPad Packet Tunnel 的 IP packet 转换为独立 TCP/UDP flow，经 DNS/FakeIP 恢复域名，按导入规则选择 `DIRECT`、`PROXY` 或 `REJECT`，并保证启动、停止、过载和网络错误都有确定结果。

v0.2 不包含：

- QUIC transport 或 QUIC Datagram；
- 多节点、负载均衡或自动故障切换；
- 规则包签名、后台分发和自动更新；
- HTTPS 解密；
- 发布自动化、证书自动续期或服务端备份系统。

## 3. 模块边界

### 3.1 Extension 内模块

| 模块 | 职责 | 不承担的职责 |
| --- | --- | --- |
| `PacketTunnelController` | 串行化 start/stop，持有本次运行 generation，统一取消与清理 | 解析业务流量 |
| `PacketIO` | 配置 `NEPacketTunnelNetworkSettings`，对 `packetFlow` 做有界批量读写 | TCP 状态机、路由决策 |
| `IPStackAdapter` | 适配经审查的 user-space TCP/IP stack，把 IP packet 转换为 TCP/UDP flow；提供 backpressure、half-close、RST/ICMP 注入 | DNS 规则或 relay 协议 |
| `DNSProxy` | 在现有 parser/core 上完成 UDP/TCP DNS 上游 I/O、action-preserving forwarding、cache 和 A/AAAA FakeIP 替换 | 通用 TCP/UDP 转发 |
| `FakeIPStore` | 在现有双栈 allocator 上增加权威 TTL、flow lease 和安全回收，维护双向映射 | 解析任意域名或作路由决定 |
| `RuleStore` | 在现有 decode/compile/atomic-write 基础上增加 byte cap、完整性校验和 current/previous 恢复，原子发布不可变快照 | 在 flow 中修改规则 |
| `FlowRouter` | 使用现有显式三分支调度，从恢复出的 domain、真实/目标 IP、port 固定 action | 在失败后改选另一个 action |
| `DirectConnector` | 新增 Network.framework 直连实现 | 回退到 relay |
| `TLSProxyConnector` | 完成并验证现有 Apple template；每个 TCP flow 或 UDP association 建立一条 v1 TLS connection | 连接池、多路复用、QUIC |
| `CredentialStore` | 使用现有协议和 Apple Keychain template 读取 32-byte token，并在 Xcode/真机验证 access group | 把 token 放入普通配置或日志 |
| `Diagnostics` | 输出聚合计数、状态、耗时与错误类别 | 输出 token、payload、域名和完整目的地址 |

`IPStackAdapter` 是 v0.2 待实现依赖。选择 lwIP 时必须固定上游版本、记录补丁、启用 IPv4/IPv6，并对 allocator、timer、packet buffer 和回调线程模型做单独评审。仅添加源码或桥接头不算完成。

### 3.2 Containing app 内模块

Containing app 负责：

1. 通过受控 UI/API 写入 relay endpoint 和非秘密参数；
2. 把 token 写入 Keychain access group；
3. 在 App Group 中导入并持久化规则快照；
4. 请求系统启动或停止 extension；
5. 展示不含敏感目标信息的状态和诊断。

Extension 只读取已验证快照和 Keychain token，不在启动关键路径解析大型 JSON 规则包。

### 3.3 Go relay

v0.2 继续复用现有 v1 relay：

- TLS 1.3 only，ALPN 为 `ipad-proxy/1`；
- 首帧携带固定 32-byte bearer token；
- server 保存 token 的 SHA-256 digest，并做 constant-time compare；
- 每个 proxied TCP flow 一条 TLS connection；
- 每个 UDP association 一条 TLS connection；
- server 继续默认拒绝 private、loopback、link-local、multicast 和 unspecified destination。

客户端规则不能替代服务端目的地址策略。

## 4. 数据流

### 4.1 启动数据流

```text
NE startTunnel
  -> PacketTunnelController.start(generation)
  -> 读取并验证小型运行配置
  -> 从 Keychain 读取 token
  -> 校验并装载不可变规则快照
  -> 初始化 FakeIPStore 与 DNSProxy
  -> 初始化 IPStackAdapter、connectors 和资源预算
  -> setTunnelNetworkSettings
  -> 启动 packet read loop
  -> state = running
  -> completionHandler(nil)
```

在 `setTunnelNetworkSettings` 成功且所有依赖 ready 前，不得读取 packet。任一步失败都进入统一回滚，关闭已创建资源，再向系统返回错误。

### 4.2 TCP flow 数据流

```text
packetFlow
  -> PacketIO 有界输入队列
  -> IPStackAdapter 重组 TCP
  -> 若目标是 FakeIP，反查原 domain
  -> RuleEngine 对 domain/IP/port 做一次 first-match
  -> FlowRouter 固定 DIRECT / PROXY / REJECT
     DIRECT -> DirectConnector -> destination
     PROXY  -> TLSProxyConnector -> Go relay -> destination
     REJECT -> 不创建网络连接，向 TCP 栈返回 RST/拒绝
  -> 返回数据进入 IPStackAdapter
  -> PacketIO 写回 packetFlow
```

域名恢复失败时，不得猜测域名。若目标不是 FakeIP，可只使用 IP 和 port 匹配；若目标位于 FakeIP pool 但映射不存在或已过期，必须终止 flow，不得把 FakeIP 当公网地址直连或交给 relay。

每个 flow 在创建时固定规则快照版本和 action。规则更新只影响新 flow，避免一个连接中途换路。

### 4.3 UDP flow 数据流

```text
packetFlow
  -> IPStackAdapter 提取完整 UDP datagram
  -> DNS destination: DNSProxy
  -> 其他 destination: 恢复 domain（如有）并固定 action
     DIRECT -> DirectConnector UDP association
     PROXY  -> v1 UDP-over-TLS association
     REJECT -> ICMP/ICMPv6 administratively prohibited；若栈无法注入则计数后丢弃
  -> 保持 datagram 边界写回 packetFlow
```

UDP flow key 为 address family、source address、source port、destination address、destination port 和 protocol。空 payload 合法。UDP association 在双向均无活动达到 idle timeout 后释放。

### 4.4 DNS 数据流

Packet Tunnel 的 DNS server 指向 extension 内 DNSProxy。DNSProxy 同时接受 UDP 和 TCP 查询。

```text
DNS query
  -> 报文和问题节验证
  -> 规范化 QNAME
  -> RuleEngine(domain, resolver-port)
     REJECT -> REFUSED
     DIRECT -> 带 DIRECT action 转发到配置的 resolver
     PROXY  -> 带 PROXY action 经 TLSProxyConnector 转发到配置的 resolver
  -> TC=1 时沿相同 action 用 TCP 重试
  -> NXDOMAIN/无相关 RR: 保留负响应，不分配 FakeIP
  -> 成功 A/AAAA: 校验 CNAME/RRset 后分配或复用 FakeIP，替换对应地址 RR
  -> 其他 qtype: 保留 action 并原样转发响应，不合成地址
  -> 写回原 transport
```

`DNSDecision.forward` 已携带选择完成的 `RoutingAction`，接入层必须据此选择 DIRECT 或 PROXY 上游。PROXY A/AAAA 采用 Fake-IP 模式时不要求客户端预先解析真实地址，真实域名由 relay 在应用建立连接时解析。DNS 超时、响应校验失败或容量不足时应返回 `SERVFAIL`，不得把 `PROXY` DNS 自动改为 `DIRECT`。

## 5. Packet Tunnel start/stop 状态机

所有状态转换由单个 actor/串行执行器管理。每次 start 创建单调递增的 `generation`，异步回调必须携带 generation；过期 generation 的回调只能释放自身资源，不能修改当前状态。

### 5.1 状态

| 状态 | 含义 |
| --- | --- |
| `stopped` | 无 packet read、flow、TLS、UDP timer 或运行期配置 |
| `starting(g)` | 正在验证依赖和设置 tunnel network settings，尚未接收 packet |
| `running(g)` | 设置完成，允许接收新 packet/flow |
| `stopping(g)` | 停止接收新工作，正在取消和回收本 generation 资源 |
| `failed(g, reason)` | 启动或运行发生不可恢复错误；只保留脱敏诊断。清理超时造成的 residual registry 会阻止同进程再次启动 |

### 5.2 转换与 completion 规则

| 事件 | 当前状态 | 动作与结果 |
| --- | --- | --- |
| `start` | `stopped` / 无 residual 的 `failed` | 创建 generation，进入 `starting` |
| `start` | 有 residual 的 `failed` | 返回 cleanup-incomplete error，请求系统重启 extension，不创建新资源 |
| `start` | `starting` / `running` / `stopping` | 返回明确的 invalid-state error，不启动第二套资源 |
| 启动成功 | `starting(g)` | 开启 read loop，进入 `running(g)`，start completion 调用一次且仅一次 |
| 启动失败 | `starting(g)` | 取消已创建资源，进入 `failed(g, reason)`，start completion 带错误调用一次 |
| `stop` | `starting(g)` | 标记取消；启动任务不得再成功；清理后先以 cancellation error 调用尚未完成的 start completion，再调用所有 stop completion |
| `stop` | `running(g)` | 进入 `stopping(g)`，执行有序关闭 |
| `stop` | `stopping(g)` | 不启动第二次清理；把 completion 加入等待列表，状态发布后统一完成 |
| `stop` | `stopped` / 已清理的 `failed` | 幂等地立即完成 |
| 不可恢复运行错误 | `running(g)` | 与显式 stop 争用同一个关闭 gate；只执行一次清理，随后进入 `failed` 并通知系统取消 tunnel |

每个系统 completion handler 都必须由 `CompletionOnce` 包装，防止取消与正常回调竞态造成重复调用。外部 completion 可能同步重入，因此必须先原子发布终态、清空 generation 资源引用，再调用 completion。

### 5.3 有序停止

停止顺序固定为：

1. 禁止创建新 flow，不再发起下一次 `readPackets`；
2. 取消 DNS inflight、pending connector 和 TLS handshake；
3. 向全部 TCP flow 注入取消，传播 half-close/RST；
4. 关闭 UDP association 并取消 idle timer；
5. 关闭 DIRECT/PROXY connection；
6. 清空 packet、DNS 和 transport 队列；
7. 销毁 IPStackAdapter 的本 generation 实例；
8. 清除内存中的 token 副本和运行期配置引用；
9. 确认 task、timer、connection、队列计数均为零；
10. 原子发布 `stopped` 或 `failed`，清空 generation 资源引用；
11. 先完成待决 start completion，再完成全部 stop completion。

正常停止预算为 5 秒。所有 adapter 的取消必须在 release gate 中证明可在预算内结束。到期后应强制取消并进入 `failed(resourceCleanupTimeout)`；若资源 registry 仍非零，则拒绝同一 extension 进程内再次 start，并请求系统终止 tunnel，不能把未清理状态发布为 `stopped`。

## 6. DNS 与 FakeIP 语义

### 6.1 查询支持

v0.2 必须支持：

- UDP DNS 与 TCP DNS；
- 单问题 A、AAAA；
- CNAME 链验证和相关回答；
- NXDOMAIN、NODATA、SERVFAIL、REFUSED；
- EDNS(0) 的安全透传或明确裁剪；
- 指针只能指向报文中已经开始的合法域名编码；拒绝指向 DNS header、非名称字段或当前/未来位置；
- 拒绝压缩指针循环、嵌套深度超过 128、越界、非法 label 和展开后超过 255 bytes；
- `TC=1` 后沿原 action 执行 TCP retry。

多问题查询、压缩指针循环、越界名称、超长报文和响应 question 不匹配均返回 `FORMERR` 或 `SERVFAIL`，且不得污染 cache/FakeIPStore。

### 6.2 域名规范化

规则与 FakeIP key 使用同一规范化：ASCII 小写并移除所有尾点。v0.2 不在运行期执行 IDNA 转换；导入方和 DNS parser 必须使用约定的 ASCII 表示。原始 QNAME 只用于构造响应，不写日志。

### 6.3 FakeIP pool 与映射

默认 pool 与现有 template 保持一致：

- IPv4：`198.18.0.0/15`；
- IPv6：`fd00:198:18:2::/64`。

部署可覆盖 IPv6 ULA；存在互联 ULA 网络时应使用部署专用的随机 RFC 4193 Global ID。启动时必须检查 FakeIP pool 与当前本地路由、relay endpoint、DNS resolver 和 tunnel address 不冲突；冲突则启动失败。全隧道配置应安装 IPv4/IPv6 default included routes，并把 FakeIP pool 和 extension DNS 地址明确纳入 tunnel；relay transport 必须由 provider 使用底层网络建立，避免再次进入自身 packetFlow。

映射 key 为 `(normalizedDomain, addressFamily)`，value 至少包含 `(fakeIP, dnsExpiresAt, activeLeaseCount, retireAfter, generation)`；同时维护 `fakeIP -> domain` 反向索引。一个 domain/family 在可用于新查询时复用同一 FakeIP。A 与 AAAA 映射相互独立。

DNS answer TTL 取上游相关 RRset 最小 TTL 与 3600 秒中的较小值，不延长上游 TTL。TTL 为 0 时响应仍保留 0；内部可在 60 秒 correlation grace 内保留映射以接住紧随响应建立的 flow，但不得把它作为有效 DNS cache entry。正向查询、反向查询或普通访问不得重置 `dnsExpiresAt`。

FlowRouter 反查 FakeIP 时必须在同一个 actor 操作中取得不可伪造的 lease；flow 结束时释放 lease。过期映射满足以下条件后才可回收：

1. `dnsExpiresAt` 已过期；
2. `activeLeaseCount` 为零；
3. 已经过 correlation grace 与 60 秒 reuse quarantine。

每族最多 4,096 条，A/AAAA 合计最多 8,192 条。容量耗尽时只可清除满足上述条件的条目，不得 LRU 驱逐未过期或仍被 flow 引用的映射；没有安全条目可回收时，新查询返回 `SERVFAIL`。停止会清除 extension 内 cache；持久化规则不等于持久化 FakeIP 映射。

当前实现已保证正向复用和诊断反查不会延长权威 TTL；生产 flow 通过原子 `acquireLease(for:)` 固定映射，grace 结束后不再发放新 lease，现有 lease 阻止回收，最后 release 后仍经过 reuse quarantine 才能复用地址。相关 ABA、重复 release、过期和并发测试已经加入 Swift core。

### 6.4 action 与 DNS 一致性

DNS query 时的 action 只决定 DNS 请求走 DIRECT、PROXY 或 REJECT。应用随后连接 FakeIP 时，FlowRouter 必须使用恢复的原 domain 和当前规则快照重新决定该 flow 的 action。因此规则更新可以影响新 flow，但不能改变已建立 flow。

## 7. DIRECT / PROXY / REJECT 失败策略

总原则是 action 固定且无隐式降级。

| action | TCP | UDP | DNS | 失败结果 |
| --- | --- | --- | --- | --- |
| `DIRECT` | 仅由 DirectConnector 解析/连接目标 | 仅建立 direct UDP association | 直连配置 resolver | DNS、connect、timeout 或 socket 错误终止当前操作；不得改走 PROXY |
| `PROXY` | 仅建立 v1 TLS tunnel，domain 目标交给 relay 解析 | 仅使用 v1 UDP-over-TLS | 经 relay 查询配置 resolver | TCP/TLS/ALPN/auth/protocol/status 错误终止当前操作；不得改走 DIRECT |
| `REJECT` | 不建 socket，向 user-space TCP 栈返回 RST/拒绝 | 不建 socket，注入 ICMP/ICMPv6 administratively prohibited；无法注入时计数后丢弃 | 返回 REFUSED | 这是规则命中，不计作 connector 故障 |

TCP connector 失败向 user-space stack 返回可观察的 connect failure/RST。UDP DIRECT/PROXY 的单个 datagram 发送失败不切换 action；可注入 host unreachable 时注入，否则按 `(action, errorClass)` 聚合计数后丢弃。协议损坏、认证失败或 TLS connection 关闭会结束整个 PROXY association。

现有 Go relay 的 TCP status 语义继续使用：`AUTH_FAILED`、`BAD_REQUEST`、`DIAL_FAILED`、`FORBIDDEN`、`INTERNAL` 都是终止当前 flow 的失败。server 的 UDP 目标解析/策略/发送失败目前按 datagram 丢弃，畸形 tunnel datagram 会关闭 association；客户端要按此不对称语义处理超时，不得等待不存在的逐包 status。

## 8. TLS transport 状态机

Swift `TLSProxyConnector` 使用 Network.framework 的标准 TLS 验证，不安装跳过信任或主机名检查的回调。

### 8.1 每连接状态

```text
idle
  -> tcpConnecting
  -> tlsHandshaking
  -> protocolAuthenticating
  -> readyTCP | readyUDP
  -> closing
  -> closed
```

任一非终态都可进入 `failed(errorClass)`，随后必须进入 `closing -> closed`。取消可从任一非终态直接进入 `closing`。状态转换必须串行化。

### 8.2 建连条件

- TLS 最低和最高版本均为 1.3；
- SNI 和证书主机名来自受控 relay 配置；
- 使用系统 trust store 或用户明确安装并选择的受控 CA；
- ALPN 必须协商为 `ipad-proxy/1`；
- 首帧必须在认证 deadline 内写出并收到合法 response；
- `StatusOK` 才进入 ready；
- token 只在 TLS 建立后发送；
- token、完整认证 request 和 response message 不写日志。

TCP connect、TLS handshake 和 protocol auth 各自默认 10 秒 deadline。取消必须终止 NWConnection 和等待中的 continuation。已有 flow 不自动重连；重连只适用于尚未交付给应用的新请求。v0.2 单节点不可达时按失败策略结束 flow。

当前 Apple template 已配置 TLS 1.3、系统信任、精确 frame read、10 秒 connection/TLS 与认证超时，并独立断言 negotiated ALPN。DIRECT TCP/UDP 也有建连超时。模板仍未在 Xcode/真机编译，Network.framework 回调与取消行为必须通过真实 SDK 和设备验证后才能称为已验证 transport。

## 9. UDP-over-TLS 限制

v0.2 使用协议 v1，限制如下：

1. 每个 UDP association 独占一条 TLS-over-TCP connection，不做多路复用。
2. 每个 datagram 使用 32-bit 大端 body length，保持 datagram 边界。
3. frame body 上限 65,600 bytes；UDP payload 上限 65,507 bytes，同时还受 target address 长度影响。253-byte domain 对应的实际 payload 上限是 65,342 bytes。
4. 不支持 SOCKS5 UDP fragmentation。iOS 侧收到超出组合 frame 上限的 UDP datagram 时返回 `EMSGSIZE`/ICMP Packet Too Big，不在 tunnel protocol 内分片。
5. 不增加协议层重传。TLS/TCP 丢包会造成 head-of-line blocking，这是 v1 已知限制。
6. 只有 association 已联系过的远端 IP:port 才可回包。server peer allow-list 必须增加每 association 上限和过期清理。
7. 双向任一 datagram 都刷新 idle timer；默认 idle timeout 为 60 秒，配置范围为 30 秒至 10 分钟。
8. control/TLS connection 关闭、认证失败、协议错误、取消或 idle timeout 都会释放 association socket、peer set、timer 和队列。

HTTP/3 测试只用于验证应用 UDP datagram 能穿过该路径，不代表底层 tunnel transport 使用 QUIC。

## 10. 规则导入与原子性

### 10.1 两阶段流程

规则导入在 containing app 内完成：

1. **prepare**：检查 byte size、严格 JSON、version、RFC3339 `generatedAt`、未知字段、规则数量和每条语义；按数组顺序编译不可变 matcher；生成内部 snapshot、metadata 和 SHA-256 完整性摘要。
2. **persist candidate**：在 App Group 同 volume 写入不可变的 `rules.<digest>.json.tmp`，同步文件后 rename 为 `rules.<digest>.json`，再同步目录。
3. **commit manifest**：生成只引用完整文件的 manifest，其中 `current` 指向 candidate、`previous` 指向提交前的 current；同目录写入并同步临时 manifest，再以一次 atomic rename 替换 `rules.manifest` 并同步目录。
4. **publish**：重新按 manifest 校验 current 文件的 size、digest、decode 和 compile，然后在 `RuleStore` actor 内用一次引用交换发布新 snapshot。

使用 versioned immutable file 加单 manifest commit，避免两次文件 rename 之间暴露无 current 状态。SHA-256 仅用于检测本地损坏，不是发布者签名。规则包签名不属于 v0.2。

### 10.2 原子可见性

- reader 只获得不可变 `RuleSnapshot`；
- reader 只能看到完整旧版或完整新版；
- JSON 解析、语义验证、编译、写盘、校验或 rename 任一步失败时，活动快照保持不变；
- extension 启动时校验 manifest 及其 `current`；current 无效则校验并装载 `previous`，同时留下 recovery 诊断；两者都无效时启动失败；
- crash 可留下未被 manifest 引用的 candidate，启动后可安全清理；不得依据文件名自动激活它；
- active flow 固定创建时的 snapshot ID；更新不重路由已有 flow；
- 不允许“空规则临时生效”或解析失败后使用宽松默认。

### 10.3 格式和资源限制

外部 JSON shape 继续以 `rules/schema.json` 为准，first-match 严格遵循文件数组顺序，未匹配时使用顶层 `final`。schema 的 500,000 是交换格式上限；iOS v0.2 为保证 keyword/CIDR fallback 成本有界，使用更严格的运行上限：

- JSON 输入最大 32 MiB；
- iOS active snapshot 最多 20,000 条规则；
- 单 value 仍为 1...1024 bytes；
- 编译后快照最大 32 MiB；
- 同时最多保留 current 与 candidate 两份内存快照；
- 超过任一限制时 prepare 失败，旧 snapshot 继续服务。

当前 core 已执行 32 MiB 输入上限、先 decode/compile、Foundation `.atomic` 写文件，再交换 actor 内 active snapshot；但尚无编译后快照 byte cap、SHA-256 损坏检测、versioned file + manifest、directory fsync 或 current/previous 回退。它们属于后续规则分发加固。

## 11. 内存、队列与并发上限

以下常量是 v0.2 的 release 配置，不得通过远端输入放大。实现可在后续版本降低上限，但提高上限必须重新做真机内存测试。

| 资源 | 上限 | 达到上限时的行为 |
| --- | ---: | --- |
| packet 输入队列 | 2,048 packets 且 4 MiB，任一先到 | 暂停下一次 read；单批仍越界则 tunnel 以 resource-limit 错误失败，禁止静默无限增长 |
| packet 输出队列 | 2,048 packets 且 4 MiB | 对应 flow 失败；持续 5 秒不能下降则 tunnel 失败 |
| active TCP+UDP flow | 1,024 | 新 TCP 返回 RST/资源不足；新 UDP 注入 unreachable 或计数丢弃 |
| 同时 opening flow | 128 | 新 flow 立即按资源不足失败 |
| 每 TCP flow 每方向缓冲 | 32 KiB | 停止从上游读取并施加 backpressure，不丢已有字节 |
| 全局 connector queue | 2,048 chunks 且 32 MiB | 暂停生产者；等待仍计入 opening flow，connect deadline 到期后只终止对应 flow |
| active UDP association | 256 | 新 association 失败 |
| 每 UDP association 每方向 | 32 datagrams 且 256 KiB | 新 datagram 计数丢弃；不得驱逐已排队 datagram |
| 全局 UDP queue | 4,096 datagrams 且 8 MiB | 新 datagram 计数丢弃 |
| UDP contacted peers/association | 256；每项 60 秒无活动过期 | 新 peer 的 datagram 拒绝；已有 peer 不受影响 |
| DNS inflight | 256 queries 且 2 MiB wire data | 后续进入 pending |
| DNS pending | 512 queries 且 2 MiB wire data | 返回 SERVFAIL |
| DNS cache | 8,192 entries 且 16 MiB | 先清除过期，再按最早 expiry 驱逐；不驱逐 inflight |
| FakeIP mappings | 每族 4,096，合计 8,192 | 只回收符合 TTL、lease 和 quarantine 条件者；否则 SERVFAIL |
| 同时 TLS handshake | 64 | opening flow 队列等待，受 connect deadline 限制 |
| 规则 JSON / 编译快照 | 各 32 MiB | 导入失败，旧 snapshot 保持活动 |

packet 输出条目必须携带 `flowID`。达到输出 hard cap 时拒绝产生越界条目的 flow，不驱逐其他 flow 已排队数据；无法归属到 flow 的 control packet 越界则使 tunnel fail closed。所有 queue 必须同时按元素数和 byte 数在 admission 前检查并计量；被拒条目只增加 rejected count，不计入 high-water。状态页可展示当前值、高水位和拒绝计数，但不展示目标内容。

Go relay 的 UDP contacted-peer set 已限制为每 association 256 项，并在 60 秒无活动后过期；确定性测试和 race detector 必须持续作为回归门禁。

## 12. 日志与诊断脱敏

### 12.1 禁止记录

运行日志、错误描述、UI、crash breadcrumb 和诊断导出均不得包含：

- bearer token、token hash 或完整认证 request；
- packet 或应用 payload；
- DNS QNAME、规则 value；
- 完整目标 IP、domain、URL、SNI 或端口组合；
- Keychain 内容和普通配置原文；
- FakeIP 与 domain 的对应关系。

### 12.2 允许记录

允许字段限于：

- 本地生成、重启后不可关联的短 flow ID；
- generation、snapshot ID 的短摘要；
- action；
- address family 和 target type（IP/domain），不含值；
- 状态转换、耗时 bucket、queue 高水位；
- 固定错误枚举，如 `tls_trust_failed`、`auth_failed`、`resource_limit`；
- 聚合 packet/byte/flow 数。

重复错误按 `(component, errorClass)` 限速，每分钟最多 10 条，额外事件只增加计数。默认日志级别不得输出 Network.framework 的敏感调试描述。token 类型继续保持 `description`、`debugDescription` 和 reflection 脱敏。

## 13. 单节点边界

v0.2 配置只包含一个 relay endpoint，不维护节点列表、健康权重或备用 relay。

- relay 或到 relay 的路径不可达时，`PROXY` flow 按失败策略结束；
- 不得因此改成 `DIRECT`；
- `DIRECT` flow 不依赖 relay，但仍受本机网络状态影响；
- relay 恢复后仅新 flow 可以重新建连；已有失败 flow 不透明恢复；
- server restart 会终止已有 TLS connection 和 UDP association；
- 状态 UI 必须把“relay 不可达”描述为单节点可用性限制，不能显示为已自动切换。

## 14. 实施顺序与完成定义

建议按以下顺序实现，每一步都保持 fail closed：

1. Xcode containing app/extension、entitlement、App Group、Keychain 与状态机骨架；
2. RuleStore 两阶段导入和原子快照；
3. IPStackAdapter 与有界 PacketIO，只做 mock connector；
4. DirectConnector 和明确的 REJECT 注入；
5. TLSProxyConnector 与 Go relay 互操作；
6. DNSProxy、FakeIPStore、TCP DNS 和 action 一致性；
7. UDP-over-TLS、idle expiry、peer 与 queue 上限；
8. 网络变化时的 fail-closed、资源释放、新 flow 重建、停止竞态、资源压力和隐私测试；不实现跨网络迁移或自动恢复已有 flow；
9. 物理 iPad 100 次生命周期、500 flows 和 v0.2 8 小时稳定性测试。

72 小时 soak 属于 roadmap v0.4，不阻塞 v0.2，但未通过该门禁前不得使用“长期稳定”结论。只有 `docs/v0.2-acceptance.md` 中所有 v0.2 release gate 都有对应环境的证据后，才能把 Packet Tunnel、DNS/FakeIP、DIRECT/PROXY/REJECT 或可安装开发构建标记为完成。
